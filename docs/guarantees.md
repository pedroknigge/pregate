# Guarantees and residual limits

Pre denies an agent tool call when the command text or the edited bytes are enough to show one of the following. The check is the real `hook pre` entrypoint. It does not run the command.

These denials apply only in a project where `pregate enable` was run. A directory that was never enabled is not enforced: every pre-command and pre-edit exits 0, including a write, a hook switch, `git commit --no-verify`, and a change to harness settings such as `~/.claude/settings.json`. SessionStart may print one line. A pending review, a pending batch, another project this session already reached, the home directory, and a parent past a `.git` boundary do not turn that enforcement on. `pregate disable` ends enforcement for that worktree, or for the whole project with `--project`, by the same check. A registered pre-command and pre-edit then exits 0 with empty stdout and does not start the engine, so it does not deny. `pregate status` still names the scope. A write that lands in a different worktree that is still enabled is still that worktree's write.

## What is denied

- A literal `pregate enable` or `pregate disable`, including `--yes`. The denial names the command and tells the human to run it in a separate terminal. Every other literal `pregate` command is allowed from the harness shell, including a `!` line: `approve` with a code or `--yes` (optional `--digest`, optional `--no-commit`), `init --yes`, `pack … --yes`, `issue submit --yes`, `feedback apply --yes`, `storage apply --yes`, `uninstall`, `setup` and `update`. A script, a substitution, `sh -c`, a Makefile or a wrapper of `enable` or `disable` is still denied. A wrapper of `prepare`, `setup`, `update` or `uninstall` is `hook-switch`. A script that only runs `approve` or `storage apply --yes` is allowed. A verb the scan cannot read literally (`pregate "$VERB"`, `pregate $(…)`) is treated as a control command. A `CI=` assignment on a `pregate` command is still denied, although `CI` no longer approves anything.
- Assigning or exporting `PREGATE_UNATTENDED_APPROVAL`, `PREGATE_ACCEPT_CONTRACT`, `PREGATE_TESTING` or `PREGATE_TEST_ANSWER` (`approval`: an agent cannot grant itself approval, and the text points at the human terminal rather than a rule adaptation), and naming PREGATE's own records (`pregate/consent`, `pregate/sessions`, `pregate/contract-approvals`, `pregate/pending`, `pregate/proposals`, `pregate/reached`) in a script or inline program (`hook-switch`). Other `PREGATE_*` assignments stay `hook-switch`.
- A shell command acts on PREGATE itself: it writes `.pregate/`, a contract, lock, config, or baseline file, or a harness file that holds PREGATE's hook entry (`.claude/settings*`, `.codex`, `.cursor/hooks*`, and the same kind of file for the other harnesses). Source files are not in that set. `echo > src/a.ts`, `sed -i src/a.ts`, and `git checkout -- src/a.ts` are allowed. The edit tools still gate source.
- Inline interpreter code or a script file that contains a literal write into a gated or protected path: `open('src/a.ts', 'w')`, `fs.writeFileSync('src/a.ts', …)`, `Bun.write('test/x.test.ts', …)`, `file_put_contents("src/a.ts", …)`, `open F, ">src/a.ts"`, and the same forms in a file passed to `node`, `bun`, `python`, `ruby`, `perl` or `php`. The denial names that path. A read, an import, `eval`, `require`, a computed path (`"sr" + "c/a.ts"`), a REPL (`node`, `python3`, `ruby`, `deno repl`) and a write whose literal target is outside the project (`/tmp/x`, a repo-root `out.txt` when scope is `src/**`) are not denied. The session snapshot is not consulted: editing the file during the session does not flip a code runner from allow to deny. Control text in that file is still denied. A bare command name found on `PATH` is read the same way when its real file lies inside a project; an installed tool outside every project is read for control commands only. The file is unreadable, undecodable, or larger than 64 MiB → `shell-admin`. A native executable is not scanned. A Python module invocation is scanned only when the dotted name resolves to a file under the working directory. A module that does not, such as `pytest` or `pip`, is not a script path. A module name that is not literal is allowed.
- Launching another harness. A harness whose hooks are installed may be launched, including non-interactive forms (`claude -p`, `codex exec`, `opencode run`, `agy`, `grok`, `cursor-agent`) and a prompt that mentions pregate or hooks. The installation is the global one from `pregate setup` or, for claude-code, codex, cursor and agy, `pregate project hooks --harness <id>`. Aliases are the same harness (`claude`/`claude-code`, `agy`/`antigravity`, `cursor`/`cursor-agent`/`agent`, `opencode`/`opencode-ai`), including a `.exe` or `.cmd` name, an absolute path, and `npx`/`bunx`/`pnpm dlx`. Cursor is gated by the shared `~/.claude/settings.json` registration it imports. A prompt is not a hook switch. A real option or subcommand still is: `--dangerously-skip-permissions`, `--yolo`, `--dangerously-bypass-approvals-and-sandbox`, `--no-hooks`, a `HOME=` override, `--settings` or `--config` that points at hooks, and `hooks` or `plugin` subcommands. An ungated harness stays `shell-admin`, and the message names that harness and the command that gates it. `gemini`, `qwen`, `copilot`, `kilo`, `amp`, `droid`, `auggie`, `junie`, `kiro-cli`, `cline` and `aider` have no registration; the message says so instead of inventing one.
- A host-automation CLI an agent uses to drive a browser or a desktop: `orca`, `orca-dev`, `orca-ide`, `agent-browser` and `agent-desktop`, including the same command after `npx` or `bunx`. An inspect or drive subcommand is allowed with consent on and with consent off (`orca console`, `orca network`, `orca snapshot`, `orca click`, `orca type`, `orca navigate`, `orca screenshot`, `orca status`, `orca skills get`, `agent-browser open`, `agent-browser click`, `agent-browser fill`, `agent-desktop screenshot`, `agent-desktop click`, `agent-desktop type`, and the other drive verbs of those tools). Read-only orca inventory is allowed on those same paths, including when the launcher file is inside the project: `ports`, `doctor`, `version`, `info`, `help`, `list`, `agent-context`, `diagnostics` and `diagnostics memory`, a second word `list`, `info`, `help` or `version` (`worktree list`, `project list`), bare `orca`, and `--help` or `-h` on any orca command. `--version` and `-v` are that inventory only when no subcommand is present. The real orca CLI's read-only commands are `ports`, `status`, `diagnostics memory`, `agent-context`, and help/version; the extra names are accepted because they only read. The launcher, including a bash script that ends in `exec "$ELECTRON"`, a `.cmd` launcher, a node shebang and a native binary, is read for control commands only. An orca verb that is not inventory, not a drive command, and not one of the denials below is `shell-admin` when that launcher is inside a project, and the message names the tool and the verb (`orca frob is not a read-only orca inventory or drive command.`) instead of the generic skip-hooks sentence. The same verb on a launcher outside every project stays allowed. `agent-browser` and `agent-desktop` are unchanged: a subcommand outside their drive loop is still project code when the file lies inside the project. `orca agent launch`, `orca worktree create --agent`, `orca automations run`, and `orca terminal create` or `terminal split` whose `--command` starts with a harness name are `shell-admin`. `orca agent hooks off` is `hook-switch`. A screenshot or other output path is an ordinary write (`screenshot`, `full-screenshot`, `pdf`, `record`, `download`, and `--output`, `-o`, `--out`, `--path`, `--file`, `--trace`, `--screenshot`, `--annotate`). A path inside the project is `shell-write` when the scope check says so, a temp path is allowed, and a path that is not literal is `shell-write`. Outside an enabled project the hook does not run this check. See [Driving a browser or a desktop](guides/daily-use.md#driving-a-browser-or-a-desktop).
- The same invocation in a literal script those interpreters execute (`python3 attack.py`, `python3 < attack.py`, `python3 - < attack.py`), in a literal shell script run by path or fed on stdin (`bash ./run.sh`, `./run.sh`, `./run` without a suffix, `bash < run.sh`, `bash -s < run.sh`), in a literal PowerShell or cmd script (`powershell -File x.ps1`, `.cmd`, `.bat`), and in a literal Makefile (`make approve`, `make -f Makefile`). The whole file is read: a control command after any amount of padding is seen, and a file larger than 64 MiB is denied rather than skipped. A backslash, backtick or caret before a line break joins the two lines first, so `pregate \` then `disable` on the next line is one invocation. UTF-8, UTF-16 and UTF-32 files (with or without a byte-order mark) are decoded; a file with NUL bytes that decodes as none of them is denied (`shell-admin`), and a native executable (ELF, Mach-O, PE) is not a script.
- `rsync`, `tar`/`unzip` extraction, and in-place formatters or fixers (`prettier --write`, `eslint --fix`, `ruff check --fix`, `biome` with `--write`, `gofmt -w`, and the like) whose destination or target path resolves inside an enabled root. List-only archive flags (`tar -t`), dry runs, and check-only formatters (`prettier --check`) stay allowed.
- A bare command name (`deploy`, as opposed to `./deploy`) is resolved on `PATH` and, when that file is a script, scanned: like a literal path when its real file is inside a project, and for control commands only when it is an installed tool outside every project. A non-literal script (`bash "$SCRIPT"`, `node "$P"`, `make -f "$F"`, `powershell -File $P`, a pipe into `sh` or `node`) is not denied: the file it will run is not visible, so it is not a proven write. A literal script that edits gated source, or that runs a control command, is still denied, and the message names the target.
- A Git command that moves history or the worktree inside an enabled root: `reset` with `--hard`, `--merge`, `--keep` or a commit (not `--soft`), `checkout <commit>` (including `--detach`), `switch` (including `--detach`), `stash` (push, `-u`, pop, apply, branch), `clean -f` (not `-n`), `cherry-pick`, `revert`, `read-tree` and `checkout-index`. PREGATE asks Git (read-only) which files the command would change and judges them as writes: a change under `.pregate/` is `protected-path`, any other in-scope file is a write. A plain `checkout <branch>` or `switch <branch>` (no other option; `switch -- <branch>` counts) of one existing branch on a clean worktree is not a write of the files that differ. The branch is a local branch, the previous branch `-`, or the single remote-tracking branch of that name. Those files arrive with the branch. A protected path among them is still `protected-path`. A dirty worktree, `--detach`, `--force`, `--discard-changes`, a new branch, a commit, a tag, or a path checkout (`checkout -- <file>`) stays a write. A form whose files Git cannot list, or a non-literal command, is denied as `shell-write`. `merge`, `rebase`, `pull` and `am` are not judged here; their result is judged by Stop, the pre-commit check and the CI ratchet like any other tree.
- Writing or editing a shell script, a Makefile, or a shebang program whose resulting text contains one of those invocations.
- Writing or editing user-level harness settings and the install/launcher paths, including `~/.claude/settings.json`, Cursor `hooks.json` and `cli-config.json`, Codex `hooks.json` and `config.toml`, Grok `config.toml`, Antigravity/agy `~/.gemini/config/config.json` and `hooks.json`, `~/.local/bin/pregate`, and the data-directory launcher. This matches the shell guard when the hook is running for an enabled project (the process directory or `CLAUDE_PROJECT_DIR`, `CURSOR_PROJECT_DIR`, or `GROK_WORKSPACE_ROOT`), including a fresh session that has not registered that root yet.
- Hook-trust edits in that scanned text (`trusted_hash` assignment, `hooks.state` assignment, `--dangerously-bypass-hook-trust`) and any mention of `PREGATE_TESTING` or `PREGATE_TEST_ANSWER`.

`pregate guide --preview`, `pregate approve --preview`, and `pregate status` stay allowed. So do the commands that read the project or prepare one review for the human: `pregate layers`, `pregate layers apply <map.json> --preview`, `pregate compile <rules.md>`, `pregate compile apply <proposals.json> --preview`, and `pregate import arkgate --preview` (optional `--config <path>`), with every word literal and no `--yes` or `--digest`. When stdout is not a terminal, the approval code is also withheld unless `PREGATE_UNATTENDED_APPROVAL=1` or `PREGATE_TESTING=1` is already set. That withholding is not what stops an agent: `pregate approve --yes` names no code.

A literal `pregate approve <code>`, or `pregate approve --yes` with an optional `--digest`, applies without a terminal. A harness `!` line is that same command. This is a convenience, not a guarantee that the agent cannot type it. An agent could run it. Pregate writes the confirmation to the approval log (`via` is `yes` when stdin is not a terminal) so a self-approval is visible. The log cannot tell a human click from that self-approval, so it does not record `via: "native-ask"`. In an interactive Claude Code parent session the hook turns that allowed command into `permissionDecision: "ask"` before it runs: Accept runs it, Reject runs nothing. A subagent, `dontAsk`, `bypassPermissions`, a remote session and `CI` do not get that prompt and keep this allow. `claude -p` has no payload field; an ask nobody answers is denied by Claude Code. In an interactive agy session the hook returns `{"decision":"force_ask","reason"}` with the same summary: Accept runs the command, Reject runs nothing. Skip-permissions, always-proceed, Turbo, print mode, a child conversation and `CI` do not get `force_ask` and keep this allow. Auto, accept-edits, plan and an explicit Default still get `force_ask`. Antigravity 1.5.7 made Auto the default where that mode is available; it is not always-proceed. Codex, Cursor, Grok and OpenCode keep the allow and do not receive a hook ask. A denial of a different approval attempt tells the agent, in that Claude parent or agy session, that it may propose the literal command. Elsewhere the hook text tells the agent to ask the human and not to run the command. A bare `pregate approve` still asks for `y` on a terminal. `enable` and `disable` are not this path: the hook denies them, and `--yes` on the command itself still needs a terminal or `PREGATE_UNATTENDED_APPROVAL=1`. Every other command that asks for consent accepts `--yes` from a harness shell with no terminal and without that variable. The approval log records that confirmation as `via: "yes"`. A pipe that contains `y` is still not a typed `y` for a command that did not pass `--yes`. Without `--yes`, those commands apply only when:

- `PREGATE_TESTING=1` supplies `PREGATE_TEST_ANSWER` on a test build, or
- `PREGATE_UNATTENDED_APPROVAL=1` is already set in the environment of the process (an unattended CI job opts in this way; `CI` alone does not, because tools and agent sessions set it), or
- stdin is an interactive terminal and the human types `y` on `/dev/tty` (or `CONIN$` on Windows).

A pipe, including one that contains `y`, is not that typed `y`. Recomputing the digest from the proposal file does not satisfy a bare `approve`. An agent shell cannot set `PREGATE_*` or prefix `CI=` onto `pregate`. A harness that starts the agent with `PREGATE_UNATTENDED_APPROVAL=1` already in its environment gives the agent the same power as that CI job: do not set it where an agent runs. Outside an interactive Claude Code parent and an interactive agy session, a native permission prompt does not approve on the human's behalf. In those sessions, Accept on the approval-command ask runs the command the agent proposed, and the approval log still records `via: "yes"`.

The in-harness form is allowed by the shell guard on Claude Code, Codex, Grok, Cursor, OpenCode and agy, including a `!` line. Earlier builds refused it and named a separate terminal. On agy 1.5.6 that refusal was because stdin was not a terminal; the earlier agy note was only 1.2.17. Those observations describe that older gate.

## Contract loosening

A change that makes the contract looser (a rule's enforcement from `enforce` to `advisor` or `shadow`, a project default lowered, a rule removed or downgraded) is compared against a reference, not trusted because the lock matches the preset:

- **Stop** compares the lock at the start of the session with the lock on disk, and **pre-commit** (`check --staged`) compares `HEAD` with the staged lock. Both block (`contract-loosened`) unless this machine holds an approval record for that exact lock: `pregate approve`, `pregate preset apply` and `pregate preset compile` write one after confirmation. The record and the append-only log say whether that confirmation was a terminal, a non-terminal `--yes`, CI, or the test hook. The records live under the user's data directory; a process running as the same user can forge them, so they keep an honest agent on track and are not the boundary.
- **`check --ratchet`** compares the base lock with the head lock and fails on any loosening, whatever local records say. It prints a digest of that exact base and head pair. The check passes only when `PREGATE_ACCEPT_CONTRACT` in the job's environment lists that digest. The CI template reads it from the repository variable `vars.PREGATE_ACCEPT_CONTRACT`, which a pull request cannot change. This is the boundary: protect `.pregate/` and `.github/workflows/` with CODEOWNERS and required reviews, or a pull request can rewrite the workflow that runs the check. The template runs the engine that the base branch's lock pins, so a change cannot pick an older engine that lacks this check by editing its own lock.
- **The Vercel build** runs that same check before the framework build. A preview reads the engine pin from the merge base with the production branch, not from the commit being built. A non-zero exit fails the deployment. `vercel.json` and `scripts/pregate-vercel-build.sh` are part of the change under review, just like a workflow file: protect them with CODEOWNERS. `pregate ci status` fails closed when a required provider (Actions, Vercel, or both) is missing, still running, or failing.
- `preset compile` without a human at the terminal refuses to write a looser lock. A script that edits the preset and recompiles is a control command for the shell guard; the compile itself still asks.

## Consent removed during a session

Consent records and session state live in the user's data and state directories, which any process of that user can change. PREGATE cannot prevent that; it detects it. When a root the session reached is disabled or its consent record is gone, Stop says so in its notice, and `pregate status` warns for a day after any recorded session of that root.

`pregate disable` is human-only. With no extra flag it marks the current worktree, the checkout of the current branch, and withdraws the repository-wide consent other worktrees were inheriting. A worktree enabled by name stays enabled, and a worktree added afterwards is inert until enabled. `pregate disable --project` marks the repository, and every worktree of it stops, including one enabled by name. `pregate status` says which scope applies, and a worktree disable also names the branch checked out there. Pre-command and pre-edit then exit 0 and block nothing in that scope, including a session that had already reached it: `git commit --no-verify`, an ungated harness, an ordinary source edit, `pregate approve --yes`, `pregate enable`, a hook switch, and a write to harness settings. The hook may print one informational line and does not deny. A command whose path lands in a different worktree that is still enabled is still that worktree's write. A project that was never enabled is not this path: a pending review there still guards project writes.

Reads are not hooked (MH-22): the Pre matcher stays a closed list of edit and command tools, so a project that never ran `pregate enable` pays nothing for a `Read`, `Grep` or `Glob`. The pending-proposal file is readable by a tool that reads files; what it holds is the digest, and knowing the digest is not approval (the terminal rule above). The shell guard still denies shell reads of the proposal directory.

Benign commands stay allowed: `python3 -c "print(1 + 1)"`, `node -e "console.log(1)"`, `pregate status`, a shell script that only echoes, and `make` on a Makefile that does not name a control command. Inside an enabled project, registry reads (`npm view`, `npm info`, `pnpm view`), package installs (`pnpm install`, `npm ci`, `pnpm add`, `bun install`, `yarn`), `git init`, `docker` and `docker compose`, and build, test, and dev runners (`next build`, `tsc`, `vitest run`, `pnpm test`, `pnpm dev`) are allowed. The package.json script or Makefile recipe they run is scanned: a script that edits gated source or runs a pregate control command is denied, and the message names the write target. `pnpm lint`, `pnpm gate`, `npm run lint`, `yarn gate` and `bun run gate` are that script, the same as `node` on the file the script names. A name package.json does not define, such as `npm publish`, is denied by name. Editing the script file during the session does not change that verdict. A shell builtin (`cd`, `read`, `type`, `wait`, `umask` and the like) is not looked up on `PATH`: the shell runs it itself, and the script macOS ships as `/usr/bin/cd` is never what `cd src` runs. A Bun subcommand (`bun test`, `bun run`, `bun install`) is not read as a script file of that name. What the guard still refuses among routine commands is measured in [Shell guard friction](benchmarks/shell-guard-friction.md). Prose is not an invocation: a comment line that mentions `pregate` followed by a line that starts with `install:` or `update()`, and a comment such as `# CI = GitHub Actions; run pregate status`, are not denied. The scan drops lines that are only a comment and does not let plain whitespace join `pregate` to a verb on the next line; a quoted argument list (`'pregate',` then a quoted verb on the next line) is still one invocation.

## Residual limits

These are heuristics over text, not a sandbox.

- The scan does not execute the program or expand variables. Concatenation (`'pre' + 'gate'`), `base64`, `chr()`/`bytes` built strings, encodings the decoder does not recognize, and a variable whose value is not in the scanned text are not recognized.
- A bare name is resolved on `PATH` only as a file this process can see. A name built by concatenation, and a script whose bytes are an encoding the decoder does not recognize, are still not read.
- A comment that is not a whole line (`echo ok # pregate approve x`) is scanned like code; a control command hidden in a string that is never executed is denied like one that is.
- A Write of a `.py` or `.js` file that is not a shebang script is not denied for control text. Executing that file with a literal interpreter command is denied when the file text contains a control invocation. `python3 -c 'exec(open("a.py").read())'` is denied only when that one-liner itself names a control command.
- Knowing the digest is not enough for a bare `pregate approve`: that form still waits for `y` on `/dev/tty` or `CONIN$`. A code operand or `--yes` on that command, and `--yes` on every other pregate command except `enable` and `disable`, applies without a terminal. The approval log records it as `via: "yes"`. An interactive Claude Code parent, and an interactive agy session, ask before `pregate approve` runs; Accept is what runs it. Assigning `PREGATE_UNATTENDED_APPROVAL` on a command, in a script or in inline code is denied as `approval`. `enable` and `disable` stay on a separate terminal.
- Inline interpreter sinks are a list. A program that reaches a write through a name the list does not hold, or through a file it imports, is not seen here; Stop, pre-commit and CI judge the files it wrote.

### Shell residual bypasses the guard still does not see

| Attack | Pre shell guard | Backstop |
| --- | --- | --- |
| A literal dynamic command the scan does not execute (`eval 'echo ok'`, concatenation, `base64 -d`, `chr()`/template-built strings) | Not denied by itself | Stop, `check --ratchet`, CI |
| Encoded or compressed payloads the decoder does not recognize | Not read as a script | Same |
| Write sinks only in a module the script imports (no sink token in the file text) | Not denied at Pre | Stop, pre-commit, CI |
| In a node script file, access built through `constructor`, `prototype`, `globalThis` or a computed member, with no sink name in the text | Not denied at Pre | Same |
| A project script that already uses a sink, changed in the session so that the same call writes another file (new arguments, the same name and member) | Not denied at Pre | Same |
| A project script that already writes files when the session begins, run unchanged | Not denied: it is the project's program, as under `pnpm test` | Same |
| `rsync`/`tar`/`prettier` with destinations built at runtime, not spelled on the command line | Not denied | Same |
| MCP and other edit channels with no Pre matcher | Hook may not run; in Cursor, Pre judges the absolute paths an MCP call names | Stop, CI |
| Background/async writers (`&`, `nohup`, harness-specific delays) | May exit Pre before the write | Stop, CI |
| Git `merge`/`rebase`/`pull`/`am` | Judged after the fact | Stop, pre-commit, CI |

Stop, pre-commit, and the CI ratchet remain the deterministic boundary for anything Pre does not establish from the command text alone.
- Git history commands are judged by the files Git reports for them before they run. A hook, a filter or an alias that Git runs as part of the command is not.
- Local approval records and consent records can be rewritten by any process of the same user. Stop and pre-commit trust a matching approval record; only the CI ratchet with a repository variable is outside the agent's reach.
- A direct `pregate prepare`, `pregate setup` and `pregate update`, including `--yes`, runs from the harness. A wrapper (`sh -c`, `env`) of those commands stays denied. They do not ask the human for `y` on a terminal when `--yes` is present: they add or refresh protection rather than remove it.
- `script`, `tmux`, and `screen` are denied as interactive sessions. A non-literal script path (`bash "$SCRIPT"`, `node "$FILE"`) is not a proven write and is allowed. `eval` of a command this process cannot read stays `shell-write`, including `bash -c 'while read l; do eval "$l"; done'`. `env -i` is `hook-switch`. `env -u` of `PREGATE_UNATTENDED_APPROVAL`, `PREGATE_TESTING`, `PREGATE_TEST_ANSWER`, or `PREGATE_ACCEPT_CONTRACT` is `approval`. `env -u` of any other `PREGATE_` variable stays `hook-switch`. Codex can still give `exec_command` a pty when `tty` is true, and `write_stdin` types into that pty without another PreToolUse. The PreToolUse payload is only `{command}`; it does not include `tty`. The read/eval loop above is denied before that child starts, so `write_stdin` has no terminal to type `pregate approve` into (`test/codex-pty-approve.e2e.test.ts`). Another pty allocator, or an obfuscation the lexer does not read as a non-literal script, can still give a child a terminal, and a terminal prints the approval code.
- Where a project is enabled, shell syntax the lexer cannot finish denies (`shell-uncertain`): an unclosed quote, an unclosed `$( )` or backtick, an unclosed arithmetic expansion, an unclosed `[[` test, an unclosed `{` group, or a heredoc with no terminator. A finished token the heuristic does not classify, such as `select` or `coproc`, is not a deny by itself. A command whose working directory was never enabled is not checked at all. The hook exits 0. A harness project variable pointing at an enabled project still protects that project's harness settings.

## What the adversarial suite holds pregate to

`test/adversarial.e2e.test.ts` runs the compiled `pregate` binary against disposable
git repositories. The table is the claim those runs lock in. **Sound** means the
attack in that row cannot pass a consented check or hook. **Best-effort** means
pregate covers a stated slice and misses the rest on purpose or because the
comparison does not see it. **Not applicable** means the boundary belongs to
something outside pregate.

`no-new` (see `src/ratchet.ts`) counts violations. It does not prove two programs
are the same.

### Ratchet (`no-new`)

| Case | Verdict | What the binary does |
| --- | --- | --- |
| Violation moved inside the same symbol | Sound | The count for that rule and symbol is unchanged, so the move is not new debt. A second site in the same symbol is denied. |
| One violation removed and a different one added in the same function | Sound | Swapping two matches of the same rule is net zero. A different rule is not compensation and is denied. |
| Equivalent code in different syntax | Best-effort | Modeled forms of one rule (`as unknown as`, parentheses, `as any as`) stay one violation and are denied when newly introduced. Pregate does not decide that arbitrary programs are equivalent. |
| Symbol renamed, duplicated, or extracted | Sound | An unchanged function body in the same file keeps its debt across a rename (`parseBody` to `parseBody2`), a move onto another symbol, or an extraction that leaves the old name with a different body. The declared name is outside the body hash. Only the violations the old symbol no longer carries can follow its body, each once: a copy next to an original that still has the violation, with the same body or a changed one, is new debt. A body moved into a different file is not paired. |
| Import hidden behind a barrel or a path alias | Sound | A re-export and a `tsconfig` `paths` alias are resolved, including a package name that an alias points at a local file. A chain past three re-export hops fails closed (`unresolvable-import` or the layer edge on the hop that is still visible). |

### Trust boundaries

| Case | Verdict | What the binary does |
| --- | --- | --- |
| Lock bytes edited by hand | Sound | `check` rebuilds the lock and rejects bytes that are not the compiler's output. A hook write while that lock is stale is `lock-stale`. A preset write through an edit tool is denied and not applied (an invalid document is an invalid contract change; other files under `.pregate/` are `protected-path`). `git commit --no-verify` is `shell-admin`. |
| Contract loosened by a script (preset edited, lock recompiled) | Sound in CI, best-effort locally | The lock then matches the preset, so the rebuild alone cannot see it. `check --ratchet` compares the base lock with the head lock and fails on any loosening unless the repository variable `PREGATE_ACCEPT_CONTRACT` lists that loosening's digest. Stop and pre-commit block it without a human approval record on this machine; a same-user process can forge that record, so the local checks are best-effort. The shell guard denies the literal and scripted `preset compile`/`apply`, and `preset compile` asks the human before writing a looser lock. |
| Git history commands that rewrite `.pregate/` | Sound for the listed commands | `reset`, `checkout <commit>`, `switch`, `stash`, `clean`, `cherry-pick`, `revert`, `read-tree` and `checkout-index` are judged by the files Git says they change; a change under `.pregate/` is `protected-path`. A clean `checkout` or `switch` of one existing branch is not an in-scope write; a `.pregate/` change on that branch is still `protected-path`. `merge`, `rebase`, `pull` and `am` are judged afterwards by Stop, pre-commit and the ratchet. |
| Consent removed or disabled by a script | Detected, not prevented | Stop's notice and `pregate status` warn when a root the session reached lost its consent. |
| Symlink that leaves the repository | Best-effort | A new symlink is read through, so its target is judged. An edit or shell redirect whose spelled path the lock judges, and whose real target sits in no enabled root, is denied (`protected-path`). A target in another enabled root, such as a nested one, is judged by that root. A spelled path out of scope stays out of scope. Two gaps are skipped below. |
| Parallel worktrees and consent | Sound | Enabling one checkout consents every linked worktree of that repository. A clone does not inherit it. `pregate disable` turns off that worktree and withdraws the shared consent; a checkout that was enabled by name stays enabled, and a worktree added afterwards is inert until enabled. `pregate disable --project` turns every worktree off, including one enabled by name. `pregate enable` restores the shared consent. A worktree disabled by name stays off. |
| Partial or invalid reconstructed edit | Sound | An edit whose old text is missing or not unique is `tool-will-fail`. A patch that does not match, and a pure insertion hunk, are `cannot-reconstruct`. An exact unique edit of clean code is allowed. |
| Hook process fails midway | Sound | The real engine exiting 1 is a denial, not an allow, inside a directory `pregate enable` covers, unless that project's preset sets `"uncertainty"` to `"open"`. A supervised child that prints an allow and then exits after the `rules` checkpoint does not have that stdout forwarded. A directory that was never enabled, and a checkout that was disabled, exits 0 with empty stdout before the engine starts, including when the engine is missing, exits non-zero, or would hang. On Grok Build ≥ 1.0.71 that empty allow still passes under `failClosed`. Cursor's native preToolUse prints `{"permission":"allow"}` for that allow, because empty stdout under `failClosed` would block. See Grok Build hook supervision. |
| Non-literal script | Allowed | `bash "$SCRIPT"`, `node "$P"`, `make -f "$F"` and a pipe into `sh` or `node` are not denied. The file is not visible, so the command is not a proven write. A literal script that edits gated source or runs a control command is still denied. |
| Script found on PATH | Sound for control commands, best-effort for writes | A bare command name is resolved on PATH. A script whose real file is inside a project is scanned like a literal path. An installed tool outside every project is scanned for control commands only, and only inside a project where `pregate enable` was run. A directory that was never enabled is not checked. A script planted in a PATH folder outside the project can write project files without a Pre denial. Stop, the pre-commit check and the CI ratchet judge the resulting tree. |
| Host-automation CLI | Sound for the drive and inventory subcommands | `orca`, `orca-dev`, `orca-ide`, `agent-browser` and `agent-desktop` may inspect or drive a browser or a desktop, with consent on or off, including through `npx` and `bunx`. Read-only orca inventory (`ports`, `list`, `info`, `version`, `help`, `--help`, `--version`, `doctor`, `diagnostics`, `agent-context`) is allowed on both paths. The launcher is read for control commands only. Launching an agent is `shell-admin`. `orca agent hooks off` is `hook-switch`. An orca verb outside that list, when the launcher is inside a project, is `shell-admin` and the message names the tool and the verb. An output path inside the project is `shell-write` when the scope check says so; a temp path is allowed. |
| Interpreter one-liner | Allowed unless it writes a PREGATE file | `node -e`, `python -c`, `ruby` and `bun -e` run, including a literal write of a source file. A literal write of `.pregate/` or another protected PREGATE path is `protected-path`. |
| Unreadable or malformed status or lock JSON | Sound | A lock or preset that is not JSON is `lock-stale`. One the process cannot read (`EACCES`, or a path that is not a file) is denied. It is not treated as permission to edit. |

### Grok Build hook supervision

The shared PreToolUse handler in `~/.claude/settings.json` sets `failClosed: true`. That is the file Grok runs. Pregate does not also write `~/.grok/hooks/`.

Grok Build 1.0.71 documents the field ([changelog](https://x.ai/changelog/build)). It was measured on the 1.0.77 and 1.0.70 Linux binaries on 2026-11-16, headless, against a local mock chat API, with no xAI account. The record is `test/fixtures/grok-failclosed-observed.json`. A live re-run is `test/grok-failclosed.e2e.test.ts` when `PREGATE_GROK_BIN` or `grok` on `PATH` is Grok Build. CI skips that re-run. It does not download the binary.

On 1.0.77, with the field set, a deny (exit 2 and the PreToolUse deny JSON) blocks the tool. A hook that exits 1 blocks. A hook that sleeps past its timeout blocks. A body that is `{` and exits 0 blocks. The same three results hold when the hook is only in `~/.claude/settings.json`. An allow is still empty stdout and exit 0, and the write lands. That is the opposite of Cursor, where empty stdout under `failClosed` blocks. 1.0.70 accepts the unknown field, still blocks a deny, and still lets a crashed hook through.

A directory that was never enabled, and a checkout that was disabled, exits 0 with empty stdout before the engine starts. The Unix launcher and the Windows launcher both make that decision before starting the engine. A directory `.git` is answered in-process, without git. A worktree, a parent walk, and an unknown git still use `consented()` on Unix, and the same records on Windows. A worktree disable record and a project disable record are not enforced, and a probe that fails before any candidate is enforced exits 0. The engine is not started, so a missing binary, a crash, or a hang cannot reach Grok's hook timeout. On 1.0.77 that empty allow still passes under `failClosed`. The same is true when another project on the machine is enabled: only this directory's own record matters. A file the payload names inside an enforced root still runs the engine, and a crash or a timeout there denies the tool.

Stop and SessionStart do not set the field. Grok ignores it on those events. Project Claude hooks do not set `failClosed`. The repository-owned PreToolUse handler written by `pregate project setup` sets Claude Code's `onFailure` to `block`. Stop and SessionStart of that file do not. Cursor's import of the shared field is still recorded as forced off and was not re-measured.

### Codex CLI version

PREGATE requires Codex CLI **0.167.0** or newer. Codex **0.166.x** and older are
unsupported: direct Guardian review on those releases did not run PreToolUse hooks
before approval policy, so a deny could be lost on that path
([openai/codex#58368](https://github.com/openai/codex/pull/58368)). Normal
PreToolUse hook execution and the `pregate doctor` canary still exercise the
direct hook route; they do not prove Guardian-path behavior on an old Codex.
`pregate doctor` prints an explicit warning when the Codex binary on `PATH` is
below 0.167.0.

### Known gaps

These tests stay skipped unless `PREGATE_RUN_KNOWN_GAPS` is set. They record a limit rather than a passing attack.

- **External target of a committed symlink.** Git diffs the link text. Changing the file outside the repo, without a hook write through the in-repo path, is not a `check --ratchet` diff.
- **Directory symlink out of the repo.** The workspace walk does not follow a symlink directory, and git lists the link rather than the files behind it. Violations that exist only there are not in the diff.
