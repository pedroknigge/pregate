# Release 0.0.14

**Pregate** `v0.0.14`, core `0.0.1`. macOS ARM64 stays the stable platform. Linux and Windows archives stay experimental until native validation is recorded.

Install 0.0.14 with `pregate update`, then run `pregate setup` once. The registered hook commands changed their failure path, and the commands an older setup registered still deny when the launcher is missing. No project needs a step after that: any engine version reads any project.

This release changes what a hook does on your machine. In an enabled project a hook now blocks on two things only: a rule the project set to enforce, and an agent acting on Pregate itself. Everything else is one line and the call goes through. CI is where a pull request is held.

The reason is a real session. A merge brought in a contract that was looser than the one the session started with. Stop compared the two, found the loosening, and blocked the end of every turn. The agent had no way out: it cannot approve for the human, and the contract on disk was the correct one. That session was blocked 22 times in advisor mode, where no rule was meant to block at all.

## What blocks locally

A hook (pre-edit, pre-command, Stop) blocks on:

- a rule the project set to `enforce`
- the control causes, where the agent acts on Pregate itself: `protected-path` (a write to `.pregate/`, to Pregate state, or to harness settings), `request-invalid`, `shell-admin` (this includes an agent that runs `pregate enable` or `pregate disable`), `hook-switch`, and `approval`

A block for a control cause is two sentences: what the agent does not do, and what to do instead.

Every other cause is one line, `PREGATE NOTE <cause>: ... Not blocked.`, and the call goes through:

- an edit Pregate could not rebuild (`tool-will-fail`, `cannot-reconstruct`) or a call it does not recognize (`payload-unrecognized`)
- a file that does not parse (`syntax`) or an import it cannot resolve (`unresolvable-import`). These two print a warning line.
- a shell command that writes a project file (`shell-write`) or has unfinished syntax (`shell-uncertain`)
- a contract it cannot use (`lock-stale`, `version-mismatch`) or a looser one (`contract-loosened`)
- state and Git problems (`snapshot-missing`, `state-io`, `git-missing`, `git-not-repository`, `git-error`) and `regex-limit`

A note means Pregate did not check something. An agent that already got a note for a file does not get it again in the session.

`pregate check` in CI stays strict and still fails on these causes.

## A looser contract is held in the pull request

Stop no longer compares the contract at the start of the session with the contract on disk. A merge, a pull, or a branch switch that brings a looser contract does not block the end of a turn.

Pre-commit (`check --staged`) prints `PREGATE NOTE contract-loosened` with the changed lines and the digest. It does not refuse the commit.

`check --ratchet --base <sha>` in CI fails on a looser contract, as before. A maintainer accepts it with `PREGATE_ACCEPT_CONTRACT=<digest>`, as before. The pull request review is the approval. No approval record on the machine is required or read.

## Any engine version reads any project

When `.pregate/pregate.lock.json` was written by another engine or core version, is behind the preset, or is missing, the engine rebuilds the lock in memory from `.pregate/preset.json` and judges with that. A hook call is no longer handed to the engine the lock pins, so that engine does not have to be installed. A pull, a branch switch, or an engine update does not stop a call.

`pregate update` installs the newest engine and needs no step in each project. `pregate update --project --preview` still prepares a review that moves the committed lock to the installed engine. Nothing local requires it.

In CI, `check` still fails when a lock the same engine version wrote does not match the preset, and tells you to run `pregate preset compile` and commit the lock. A lock from another version is judged from the preset.

## Failure is open by default

The preset key `uncertainty` now defaults to open. An engine crash, a timeout, and a missing launcher let the call through. Set `"uncertainty": "closed"` in `.pregate/preset.json` to make a hook deny those failures. Only that exact value does it.

Before this release the default was closed and `"open"` was the opt-out. A preset that does not name the key changes behavior with this release.

## One command to set a project up

`pregate enable` in a project with no contract prepares the advisor contract that `pregate guide --preview` proposes, shows a short summary (scope, packs, rules, mode), and applies it on your `y` or `--yes`. In advisor mode every rule informs and none blocks.

`pregate guide --preview` is still there when you want to choose packs, a layer map, or another mode before the first approval.

## Shorter output

An advisor finding is one line per rule. The headline already names `pregate explain <rule>`, and the text ends with `Advisory: not blocked.` A rule already told to this agent for this file is not repeated in the session. The session-start briefing lists only the rules that can block and gives one count for the rest.

`pregate status` is three lines: the state, a `Needs attention:` or `Note:` line when there is one, and `Next:` with one step. `pregate status --verbose` is unchanged.

`pregate --help` prints seven everyday commands. `pregate --help --all` prints the full usage.

The `/pregate` skill is one page: what blocks, six common requests, and what to do when a finding is wrong.

## Also in this release

The shell guard allows a command that only reads the contract: `git status`, `log`, `diff`, `show`, `ls-files` and `blame` on `.pregate`, and `head`, `tail`, `wc`, `grep`, `rg`, `jq` and `stat` on a file inside `.pregate/`. A write there is still denied.

## What this release does not establish

- A repository without CI that runs `pregate check --ratchet` has only notes locally. Nothing holds a loosened contract there.
- A note is not a check. A shell write to source, an edit Pregate could not rebuild, and a file that does not parse are written without a verdict at that moment. Stop and CI judge the files that result against the enforced rules.
- `pregate enable` and `pregate disable` are still human commands. The shell guard denies them when an agent runs them.
- A write under `.pregate/`, to Pregate state, or to harness settings is still denied.
- No rule was disabled, downgraded, or removed. A rule set to enforce still blocks.
- The project launcher at `.pregate/bin/` still runs the engine the lock names. Run `pregate prepare` for it.
- The full suite does not run on macOS in CI. macOS runs the latency and release-build jobs there, and the suite on the maintainer's machine. Linux and Windows archives stay experimental until native validation is recorded.
