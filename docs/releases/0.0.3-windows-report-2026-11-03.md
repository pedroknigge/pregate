# 0.0.3 on Windows: field report (2026-11-03)

This report covers one attempt to follow [the Windows verification guide](../guides/windows-verification.md)
for the published v0.0.3 release. It was run on an everyday Windows workstation
with other applications open, not a clean VM. **The result is incomplete. Neither verifier run
produced a `report.json`, and the manual checks were not run.** It is not a
PASS or a FAIL for v0.0.3. Some failures look like real Windows defects or
Windows-incompatible tests. Others are timeouts on a machine short of memory.
Each finding below is labelled with that classification, and with what was
executed and what is only inferred.

None of the test files or scripts named below changed between `v0.0.3` and
`main` at `e2d42353`, so the findings that are not timing-related should still
reproduce on `main`.

## Findings

### A. Probable product defects on Windows

**A1. `pregate demo` exits 1 when `python3` is the Store App Execution Alias.** (Executed.)
`test/demo.test.ts`: Python, Go and all-language demo tests fail in under 600 ms with:

```text
EACCES: permission denied, stat '%LOCALAPPDATA%\Microsoft\WindowsApps\python3.exe'
  at realpathSync (node:fs:382:27)
```

The Go demo fails too, so the tool probe resolves every candidate on PATH before it
runs any one language. The aliases under `WindowsApps` are `IO_REPARSE_TAG_APPEXECLINK`
reparse points: `lstat` says they are not symlinks, and `stat`/`realpath` raise `EACCES`.
They are present by default on Windows 10/11, so a real `pregate demo` on a stock machine
likely fails the same way. Suggested fix: treat `EACCES`/`EPERM` from `realpath`/`stat` on
a PATH candidate as "cannot resolve" (that tool not verified, or try the next PATH entry)
instead of failing the demo.

The test "a failing compiled engine is surfaced and its temporary installation is removed"
also fails, in 162 ms, with `JSON Parse error: Unexpected EOF` (empty stdout). It runs the
same Python path from source. It may have the same cause; not confirmed.

**A2. `pregate setup` exits 1 when Codex is installed and its trust is not confirmed.** (Executed in a test; impact on a real install inferred.)
`test/adversarial.e2e.test.ts` fails in `beforeAll`:

```text
error: setup exited 1
...
Hooks registered in ...\home\.claude\settings.json.
ERROR: Codex: Codex did not confirm trust for the PREGATE hooks. Left ...\home\.codex\hooks.json unchanged.
Installed /pregate skills. Global hooks remain inert until local worktree consent.
```

There are two issues here.

1. The test isolates `HOME` but keeps the real `PATH`, so the outcome depends on which
   harnesses the tester has installed.
2. `install.ps1` runs `pregate setup`. If one harness that cannot be wired fails the
   whole setup, a user with Codex installed may get a failed install even though
   Claude Code was wired. This was not checked by running `install.ps1`.

Worth deciding whether an unconfirmed harness should be a warning, with the exit code
reserved for the case where no harness was wired.

**A3. Per-step verifier limit did not end `windows-suite` in run 2.** (Observed; root cause not found.)
`scripts/verify-windows.ts` spawns each step with `timeout: 60 * 60 * 1000` for
`windows-suite`, but in run 2 that step lasted from 19:50 until at least 01:20 while the
machine was awake. `windows-bootstrap` in the same run ended after ~22 min, which matches
its 20-minute limit. Possible causes: the timeout kills `bun test` but not its child
processes on Windows, or the parent never regained the CPU under memory pressure. A
`taskkill /T`-style tree kill on timeout would make the limit hold either way.

### B. Tests that assume a POSIX-like Windows machine

These fail for reasons unrelated to Pregate's Windows behaviour. Each one needs a skip or
a portable variant.

**B1. `test/register.test.ts` › "a quote in the data path cannot break out of the command"**: needs `sh` on PATH.

```text
error: Executable not found in $PATH: "sh"
```

Git for Windows does not add `sh` to PATH by default. Skip on `win32`, or resolve
`sh.exe` from Git's install directory (`git --exec-path`/../../bin).

**B2. `test/python-inspection.test.ts`** runs `python3 -I -c ...` and gets exit **49**.
That is the Store alias stub, which runs when the real interpreter is installed as
`python`. Skip when `python3` is the alias, or try `py -3` / `python` on Windows.

**B3. `test/repo-hygiene.e2e.test.ts` › "a fresh clone has no node_modules entry..."**: the
test makes its own clone without long paths:

```text
git checkout --detach f7fe8ac1... exited 128
fatal: cannot create directory at 'packs/architecture/checks/dependency-rule/adapter-imports-framework/fixtures/fail/controller-imports-web-framework/files/src/interface-adapters/controllers': Filename too long
```

The guide asks the tester to clone with `-c core.longpaths=true`, and the test's
internal `git clone` should pass the same flag. Alternatively, shorten that fixture path.

**B4. `test/git.test.ts` › "source/compiled Git calls terminate and reject partial output at the deadline"**:
both return `{"result": null}` instead of `{"error": "Git exceeded its 5000 ms command deadline."}`,
the source one in 524 ms. So the fake slow `git` was not the one executed, or `git status`
returned before it ran. With `PATH` set to only the fixture `bin`, Windows may resolve
`git` differently (for example a `PATHEXT` or `.exe` name mismatch), or the `beforeAll`
compile may not have produced the fake binary under load. Not root-caused.

### C. Timeouts under memory pressure (not conclusive)

These may pass on an idle machine. They are listed because the margins are tight, and
because the verifier is meant to run on colleagues' everyday machines. Measured during
run 1, with ~0.5–1 GB of free memory. `bun build --compile --minify` alone took 58–65 s
for the minify phase.

| Test | Measured | Limit |
|---|---|---|
| `onboard.test.ts` (compile in hook, `exited null`) | 120 059 ms | 120 s hook |
| `git-halt.e2e.test.ts` (compile in hook, `exited null`) | 120 066 ms | 120 s hook |
| `audit.test.ts` whole-tree audit (+ compile `exited null`) | 30 025 ms | 30 s |
| `approval.test.ts` compiled approval defaults No | 30 085 ms (`status` printed nothing, expected "is active") | 30 s |
| `approve-commit.test.ts` (4 tests) | 6.0–22.0 s | 5 s |
| `runtime.test.ts` compiled runtime consumes complete stdin | 8 517 ms | 5 s |
| `english-only.test.ts` | 9 691 ms | 5 s |
| `library.test.ts` policy-only library loading | 8 104 ms | 5 s |
| `false-positives.e2e.test.ts` offline full corpus | 5 030 ms | 5 s |
| `fitness.test.ts` deadline terminates a verifier that ignores SIGTERM | 3 722 ms | < 3 500 ms upper bound |
| `issue-transport.test.ts` deadline rejects late success | 19 443 ms | < 19 000 ms upper bound |

Suggestions:

- Compile the test engine once per run and share it across suites, rather than once
  per suite inside a 120 s hook. Several suites compiled their own `pregate.exe`.
- Treat upper bounds such as `< 3500 ms` and `< 19000 ms` as assertions about the
  deadline mechanism. On Windows with real-time scanning they could be relative to a
  measured baseline, or have a wider margin.

## Suggestions for the verifier

1. **Write `report.json` incrementally.** It is written only in `finally`. When the host or
   the user kills the process, nothing machine-readable is left. Both runs here left only
   the per-step logs. Writing the report after each step (with `"finished": null`) would
   preserve partial evidence.
2. **Keep the machine awake.** Run 2 slept for eight hours in the middle of the suite.
   Calling `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` for the run's
   duration, or at least telling the tester to disable sleep, would prevent this.
3. **Preflight free memory** and warn below a threshold (a full run here needed more than the
   ~1 GB that was free). Print an expected duration as well. Run 1 reached the suite after
   ~7 minutes, and the suite alone has a 60-minute limit.
4. **Kill the process tree on timeout** (see A3).
5. **Isolate PATH-dependent harness detection** in tests that isolate `HOME` (see A2).

## Suggestions for the guide

1. Bun: `bun upgrade` installs the latest release, not the pinned one. Give the pinned
   command:
   `powershell -c "& ([scriptblock]::Create((irm https://bun.sh/install.ps1))) -Version 1.4.4"`.
2. Say that `--report` must be a new directory **on every run**, and that a rerun therefore
   needs a new name. A protected or locked old report directory may not be deletable.
3. Add a "before you start" box. Close heavy applications and other agent sessions,
   disable sleep while the verifier runs (`powercfg /change standby-timeout-ac 0`, restore
   afterwards), and expect roughly an hour.
4. Recommend running the verifier in a plain terminal rather than as a background job of a
   coding agent. Run in the background of an agent, the host can terminate it under memory
   pressure, as happened twice here.
5. Note the known Windows prerequisites the suite currently assumes, until B1–B3 are fixed:
   `sh` on PATH, a real `python3`, and the Store aliases.
