## [Unreleased]

### Fixed

- Bundled pack false positives on engine 0.0.8. Import checks for `SB-CLIENT-001`, `SB-HELPERS-001`, and `NEXT-DOC-001` read the module specifier, not every string inside an exported function. `SB-AUTH-001` and `SB-KEY-001` leave App Router and Pages Router handlers alone. `SB-QUERY-001` requires a Supabase `.from(...).select(...)` and treats `.single()`, `.maybeSingle()`, and a mutation's returning `.select()` as bounded. `SB-RPC-001` allows a static function name, including a zero-argument call, and still denies a computed name on a Supabase import. `NEXT-SEGMENT-001` and `NEXT-PARAMS-001` leave `params` and `searchParams` alone when the enclosing block declares a local of that name. `NEXT-FONT-001` and `NEXT-IMG-001` match JSX elements, not template strings. `NEXT-LINK-001` leaves `target="_blank"` and `download` anchors alone. `REACT-BLANK-001` matches a JSX `target` attribute on that element. `REACT-HOOK-001` does not treat an `if` or ternary condition as a branch. `TDD-FOCUS-001` allows `test.skip()` and `test.skip(true, reason)` in the body of a runtime `if` inside a test, hook, or describe callback. Packs: supabase 1.2.1, nextjs 1.4.1, react 1.2.1, testing 1.2.2. No rule was disabled or downgraded.
- `security-audit/SA-GO-SHELL-001` missed `exec.Command("sh", "-c", cmd)` when the whole script is a variable, the most direct command-injection form of this sink. The check now reports that call and `exec.CommandContext(ctx, "sh", "-c", cmd)`, including `bash`, `/bin/sh` and `/bin/bash`, and it still reports a script built with `fmt.Sprintf` or `+`. A constant script such as `exec.Command("sh", "-c", "ls -la")` and a direct `exec.Command("git", "status")` stay unreported. `security-audit/execution/go-shell-string` is 1.0.1, `security-audit/obvious-sinks` is 1.0.1, and the security-audit pack is 1.0.1. `strings.Join`, a shell name held in a variable, and a renamed `os/exec` import remain outside the check.
- `pregate scan` recommends the Vue pack when `vue` is a dependency, a devDependency, or a peer dependency, and when a `.vue` file is present outside a docs site, examples tree, fixtures tree, or website folder. A server app that compiles its frontend often lists `vue` only in `devDependencies`. `react` in `devDependencies` recommends the React pack for the same reason. A devDependency still does not select Svelte, Next.js, Astro, Hono, Express, NestJS, or TanStack Query. A package such as `vue-router` or `eslint-plugin-vue` does not select Vue. A `.vue` file does not add a package owner; the recommendation stays confined to the manifest that declares `vue`.
- `JS-EVAL-001` flags a bracket call of the string literal `eval` on `window`, `globalThis`, `self`, or `global`, such as a call of `window["eval"]`, and a later call of a local initialized to the `eval` identifier, such as `const alias = eval; alias(code)`. Direct `eval(code)`, `window.eval(code)`, and `(0, eval)(code)` stay flagged. A bracket call on any other object, the string `eval` outside a call, and a method declaration named `eval` are not. The javascript pack is 1.2.2 and `javascript/safety/no-eval-call` is 1.0.2.

## [0.0.8] - 2026-11-12

Pregate now gates six harnesses, and a project can carry its own hooks. OpenCode joins through a plugin. Cursor, Codex, Claude Code and Antigravity can register hooks in the repository. A Claude Code subagent hears the project's briefing when it starts, and a Grok subagent is judged as its own session. The shell guard lets a project's own JavaScript programs run, and it lets the agent read the skill file Pregate installed. OpenCode starts on Windows. See the [0.0.8 notes](docs/releases/0.0.8.md).

### Added

- `pregate project setup` merges repository-owned Claude Code hooks into `.claude/settings.json`. The hooks run the reviewed project launcher and the engine pin from the lock. They do not fall back to a global launcher or to `pregate` on PATH. The command requires `pregate prepare` and `pregate project launcher`. It does not write the home directory, accept Claude workspace trust, or grant policy consent. A second run leaves the file byte for byte unchanged and leaves hook groups it does not own in place. `pregate doctor` reports that project scope, including a project-hook canary when policy consent is active, and it reports workspace trust separately from policy consent. `pregate project hooks` remains the registration that can be committed with no machine path, including SubagentStart and the Codex project file.
- Codex registers `SubagentStart` and `SubagentStop`: children receive bounded contract context, retain the parent's baseline and check their edits when finishing. Child commands also review unattributed runtime changes in visited roots; the parent's whole-session Stop remains the backstop. Incomplete Codex Stops and launcher failures use `systemMessage` without continuing the turn. With Codex on PATH, `doctor` queries effective project hook enablement and trust without writing configuration. `bench --harness codex` measures native patch, shell, Code Mode, cold-cache and denial routes separately from the existing Claude Code baselines.

- Claude Code subagents get the project's briefing when they start. A subagent starts with the task its parent wrote and none of the context the session received, so it learned of a rule only when a write was denied. The Claude Code registration, global and project, now holds `SubagentStart` on the `session-start` command, and the reply carries the same briefing as `SessionStart` under the subagent's event name. A subagent gets no reply when the project has no contract, when the contract has a problem, or when the project pins an engine of another version. Nothing about a decision changes: the briefing grants nothing and every write of the subagent is checked as before. Two live sessions with Claude Code 2.1.322 on 2026-11-11: with no reply to the event a subagent reported no injected context, and with the project registration a subagent quoted the first line of the briefing (`scripts/e2e-real.ts --project-hooks-only claude-code`, 4 passed). Run `pregate update` to add the event to an existing registration; `pregate doctor` reports one that lacks it. Cursor and Grok read the same settings file as Claude Code; a subagent event from either on that command exits 0 with no output. Whether they dispatch the event from that file is not established.
- `pregate project hooks --harness cursor [--preview|--yes]` registers Cursor's native hooks in the project's own `.cursor/hooks.json`: `preToolUse` with the matcher `^(Write|Delete|Shell)$|^MCP:`, `stop` and `sessionStart`, on the project launcher through `$CURSOR_PROJECT_DIR`. It is the registration Cursor's cloud agents load, since they never read the user's home. It goes through the same review and approval as the other project hooks, keeps other entries and unknown keys, and a second run changes no byte. It sets no `failClosed`: on cursor-agent 2026.11.11 a `failClosed` hook that prints nothing blocks the tool, and printing nothing is how Pregate allows; the launcher already turns an engine crash or hang into a deny. `pregate doctor` and `pregate status` report the Cursor scope (project-local only, global only, both, neither; `status --json` adds `cursorHooks`) and name the double evaluation when the project also registers Claude Code, because Cursor runs the project's `.claude/settings.json` too. A live run on 2026-11-11 with cursor-agent 2026.11.11 on macOS (`scripts/e2e-real.ts --project-hooks-only cursor`, headless with `--trust`, isolated home, no global installation) allowed a clean write, denied a forbidden one with the rule reaching the model, and denied an MCP tool that tried to write into `src/core`. Not established: the interactive trust prompt, cloud agents, and the Windows form in a real Cursor session. See [the installation guide](docs/guides/installation.md#project-local-cursor-hooks).
- `pregate project hooks --harness agy [--preview|--yes]` registers the Antigravity hooks (`PreToolUse`, `PostInvocation`, `Stop`, `SessionStart`) as the named hook `pregate-project` in the project's own `.agents/hooks.json`, running the reviewed project launcher with no machine path in the file. Foreign named hooks stay untouched and a second run changes no byte; `pregate doctor` and `pregate status` report the Antigravity scope (`project`, `global`, `both`, `none`). See [the installation guide](docs/guides/installation.md#project-local-antigravity-hooks).
- Antigravity (`agy` 1.5.6, Antigravity 2.0, Antigravity IDE) support gains native `SessionStart` (`systemMessage`), `PostInvocation` warning and halt delivery (`CAPABILITIES.agy.warnings = true`, `CAPABILITIES.agy.halt = true`), `manage_task` stdin gating (`Action: "send_input"` refused as `shell-write`; `"list" | "status" | "kill"` ignored), `write_file` `Append: true` reconstruction, `Stop` `continuationActive` reentry and `USER_CANCELED` / `TERMINAL_CUSTOM_HOOK` suppression, `~/.gemini/antigravity` IDE/App detection with direct `pregate-global` plugin installation when `agy` is not on `PATH`, and protected-path coverage for `~/.gemini/config/plugins/pregate-global` and `~/.gemini/{,antigravity/,antigravity-cli/}settings.json`. Explicit `--harness agy` and `--harness codex` flags also no longer misroute to `grok` when `GROK_HOOK_EVENT` leaks from a parent shell, and the Windows `agy` fallback checks `$p.toolCall.args.Path`.
- **OpenCode 2.2.7 is the sixth harness.** OpenCode has no hook process, so `pregate setup` installs a plugin folder at `~/.config/opencode/pregate/index.ts` and adds that absolute path to the `plugins` array of `~/.config/opencode/opencode.json` (`OPENCODE_CONFIG_DIR` respected). The plugin is a shim, not a second gate: it normalizes `execute.before` into a payload and runs `pregate hook <event> --harness opencode`, so every rule and every cause stays in `src/gate.ts`. A deny is exit 2 with the text on stderr, as in Codex, and the plugin throws that text, which fails the one call; exit 0 stdout is advice, which the plugin appends to the tool result in `execute.after`. The Stop is `experimental.idle`, and its block reason is admitted with `session.synthetic`; the session briefing goes to `session.instructions.entry.put`. The plugin is inert below a directory with no `.pregate/preset.json` above its nearest `.git` entry. The decoder reads `write`, `edit`, `patch` (the Codex grammar plus OpenCode's `*** Environment ID:` header) and `shell`, ignores the read-only tools, and refuses every other name as `payload-unrecognized`; the `execute` (code mode) tool is denied in an enabled project because no hook of 2.2.7 sees its nested calls (`cannot-reconstruct`). `pregate setup`, `uninstall`, `doctor` and `status` handle the folder and the entry; `drift` reports a missing folder, a changed folder, a missing entry and a disabled entry (a leading `-` or `!`, which setup never turns back on); the canary denies in the Codex dialect. Approval commands route the human to a separate terminal. Not established `[E2E]`: that a thrown message reaches the model, that `execute.after` content does, that an instruction entry arrives before the next request, that a synthetic message continues the turn, and whether nested code-mode calls reach `execute.before`. No model credit was available, so `opencode run` answered "Insufficient balance" and no session captured these. See [the multi-harness design](docs/MULTI-HARNESS.md#mh-25b-opencode-plugin) and `test/payloads/opencode/README.md`.
- `pregate project hooks --harness codex [--preview|--yes]` registers the Codex hooks in the project's own `.codex/hooks.json`: PreToolUse with the matcher of the global Codex registration, Stop and SessionStart, on the project launcher. The command grants no Codex trust and writes no file in the Codex home; the human reviews the hooks in Codex with `/hooks`. The registered command finds the launcher by walking up from its working directory, so it works when Codex starts below the repository root. Other hooks keep their index and a second run changes no byte. `pregate doctor` and `pregate status` report the Codex scope (project-local only, global only, both, neither), read whether the Codex config marks the project trusted, and report the hook review state as unknown. A live run on 2026-11-11 with Codex 0.167.0 on macOS (`scripts/e2e-real.ts --project-hooks-only codex`, headless `codex exec` started in a subdirectory, isolated home) measured four states. (1) Project not marked trusted: Codex does not list the project hooks, and the forbidden write is written. (2) Project marked trusted, hooks not reviewed: Codex lists the three hooks as untrusted, runs none, and the forbidden write is written; the headless output carries no notice. (3) Hooks trusted: the forbidden write is denied and the rule reaches the model. (4) Definition changed after the review (one timeout value): Codex lists the hook as modified, runs none, and the forbidden write is written. A trusted hook of the user ran in all four states. So a project registration gates Codex only after two human steps in Codex, project trust and the `/hooks` review, and any later change to the definition, including an engine update that rewrites the command, removes the gate without a notice until the hooks are reviewed again. Not established: the interactive `/hooks` review and what the TUI shows for an unreviewed hook; whether Codex runs both registrations when both exist; the Windows form in a real Codex session.
- `pregate project hooks --harness claude-code [--preview|--yes]` registers the Claude Code hooks in the project's own `.claude/settings.json`. The hooks are the ones the global registration holds (PreToolUse with the same tool matcher, Stop, SubagentStop, SessionStart) and they run the project launcher through `$CLAUDE_PROJECT_DIR`, so the command names no machine path and no `pregate setup` is needed. Other hooks, permissions and unknown keys are kept, and a second run changes no byte. The file goes through the same review and approval as the launcher; under the user's home only this project's approval record changes. A missing pinned engine denies the write and names `pregate prepare`. On Windows the command starts `project-launcher.ps1` from PowerShell; one settings file holds one platform's command. `pregate doctor` reports the Claude Code scope as project-local only, global only, both (every call is evaluated twice) or neither, and does not report a missing global installation as an error in a project-local setup; `pregate status` counts the project registration and names the double case. A live run on 2026-11-11 with Claude Code 2.1.322 on macOS (`scripts/e2e-real.ts --project-hooks-only claude-code`, headless, isolated home, no global installation) loaded the hooks from the project file, allowed a clean write and denied a forbidden one. Not established: the interactive workspace trust prompt, and a real Claude Code session on Windows. See [the installation guide](docs/guides/installation.md#project-local-claude-code-hooks).

### Fixed

- The shell guard denied a project's own JavaScript programs. Since 0.0.5 a script file that an interpreter runs is read for write sinks, and for node, bun and deno the list held `import`, `require`, `module` and `exports`, so every real file matched: `node tests/index.js`, `node --test ./tests/*.js`, `node --check lib/response.js`, `./node_modules/.bin/mocha test/x.js` and `bun src/main.ts` got `shell-write`, while `pnpm test` and `npx mocha` ran. In the session trial this stopped the test or syntax check in 4 of 4 `classnames` tasks with Claude Code and 3 of 4 `express` tasks with Codex. Two limits now apply to write sinks; control invocations are denied as before. (1) A script whose text is the text it had when the session began is the project's program and is not read for write sinks. A script that the session wrote, changed or committed, an untracked or ignored file and a file outside every root are read. (2) A script file for node, bun or deno is read by the rules for a file: a literal `import` or `require` is a sink only when it names a module that writes files or starts programs, and any computed import, `fs`, `child_process`, `vm`, `eval`, `Function`, `Bun`, `Deno` and the non-reporting members of `process` stay sinks. Inline code keeps the full list. (3) A node, bun or deno script that the session changed keeps running while it gains no sink against its base text: the same writer modules and no more uses of any sink name, counted with its member. In a rerun of the four `classnames` tasks with limits 1 and 2 only, two tasks were still denied because the agent had edited `tests/index.js`, which imports `vm`. Still denied: `./node_modules/.bin/mocha`, because an ignored file has no session base (use `npx mocha` or the package script), and a new file that imports a writer module. `docs/guarantees.md` lists the three residual bypasses this adds.
- **Cursor MCP tools are judged by the paths they name, no longer denied as an unrecognized payload.** Cursor sends an MCP call to `preToolUse` as `MCP:<tool>`, and the shared matcher is a substring search, so a tool such as `MCP:write_note` reached the gate in every enabled project and was denied with `payload-unrecognized`, a cause only a human can fix. The Cursor adapter now collects the absolute local paths in the call's arguments. A call that names none has no objection. Each path it names is judged where it lands, by its path only: a protected file is `protected-path`, a file in scope is `cannot-reconstruct` (the agent is told to write it with its file tool), and a path outside every root has no objection. Only Cursor payloads reach this code; the other harnesses are unchanged. See `docs/MULTI-HARNESS.md` MH-35.
- `redis/REDIS-KEY-001` and `redis/REDIS-SCAN-001` reported any `.get(`, `.set(` or `.keys(` call: an Express `app.get("/x", handler)` route, `req.get("Referrer")`, `app.set("view engine", ...)` and `Object.keys(obj)`. On the pinned public corpus all six maintainer-labeled findings were false, out of 3,039. Both rules now match a call only on a Redis client receiver: a name that contains `redis` or `valkey`, or `client`, `cache`, `db`, `kv`, `store`, `pub`, `sub`, `publisher` or `subscriber` in a file that imports a module whose specifier contains `redis`, `valkey` or `@vercel/kv`. `REDIS-KEY-001` also reads the key from the call's own first argument, not from a call nested inside it. A client under another name is not matched; the limit is in the pack backlog. The measured false positives are pass fixtures. The redis pack is 1.2.1, and `no-unprefixed-key` and `no-keys-command` are 1.0.1.
- `pstack/PS-COMMENT-001` reported every comment outside a marker allowlist, with the message that the comment restates the code. On the corpus five of six maintainer-labeled findings were false. The rule now also exempts a JSDoc block, a comment with an `http` or `https` URL, a comment that names a license, and a comment with a reason word (because, since, so, otherwise, instead of, rather than, in order to, to avoid, to prevent, to ensure, due to, workaround, why). A comment that carries `@deprecated` is still reported. The pattern language cannot compare a comment with the code after it, so the rule still reports comments that do not restate code, and its default severity is now `warn`, not `deny`. A preset that overrides the severity is unchanged. The measured false positives are pass fixtures. The pstack pack is 1.2.0 and `no-narration` is 1.0.1. The relation text of `maintainability/MAINT-DEPR-001` was corrected to match; the maintainability pack is 1.2.1.
- Eight rules that the agent-labeled sample measured as false on the corpus are narrowed. Each measured false positive is a pass fixture (a trap fixture for `EX-NEXT-001`), every earlier fail fixture still fails, and each limit is in the pack's backlog. The trpc, vue, tailwind, authjs, mongodb and express packs are 1.2.1 and each changed check is 1.0.1.
- The shell guard denied an agent the read of the skill file that setup installs for it. A harness that loads a skill with a shell command, as Codex 0.167.0 does with `cat <home>/.agents/skills/pregate/SKILL.md`, got `protected-path` for it; in the first real-session trial this happened in both gated Codex sessions and one of them then abandoned its task. A literal `cat` call on an installed `skills/pregate/SKILL.md`, with no option, redirection, pipe, glob, variable or wrapper, is now allowed in every harness, alone or as one step of a `;`, `&&` or `||` sequence: Codex reads the skill at the end of `pwd; rg --files ...; cat <skill>`. Every write to the skill folder stays denied, another file in that folder is not readable, and a skill folder that links into Pregate state, the installation, a rule source, `.pregate` or `.git` gives no read.
- OpenCode on Windows starts `pregate.cmd` through `cmd.exe`, so the plugin uses the engine's verdict. The earlier plugin looked for the Unix launcher and then reported that Pregate could not evaluate. Protected paths under `~/.gemini/antigravity` and `~/.gemini/antigravity-cli` match when the path is spelled with Windows backslashes.
- The skill now tells the agent to run each `pregate` command as a shell command of its own. With the read allowed, a second run of the trial showed the next step: Codex joined `git status`, `pregate --version` and `pregate guide --json` in one command, the guard denied it as `shell-admin` because `pregate guide` is allowed only as a single command, and in one of four sessions Codex stopped the task there. The guard is unchanged.
- `pregate install` deleted a project launcher that was not byte-identical to the template of the running engine: one written by another engine version, or checked out with CRLF line ends. It now keeps any file at `.pregate/bin/pregate` that is a project launcher and removes only the launcher that 0.1.0 committed. Its removal of 0.1.0 hook handlers does not touch the project registration.
- **A trial with real agent sessions, and its first run.** The run of 2026-11-11 has 48 sessions (Claude Code 2.1.322 and Codex 0.167, 12 tasks on three pinned public repositories, with and without the gate). Neither arm left a new finding, so the run shows no prevented defect; it shows the cost: 17 denial rows in the gated arm, labeled 7 true, 8 false and 2 unclear by an AI coding agent. Seven false rows have one cause, the script scan of the shell guard, fixed after the run. One gated Codex task failed with no denial: the agent read a file outside the scope as forbidden. [`session-trial.md`](docs/benchmarks/session-trial.md) has the tables and the reading. `scripts/session-trial.ts` gives each task of a committed manifest ([`session-trial-tasks.json`](docs/benchmarks/session-trial-tasks.json): 12 neutral feature and bug-fix requests on three public repositories pinned by commit) to Claude Code and Codex, headless, in two arms: with Pregate installed and the contract that `pregate guide --preview --enforcement enforce` proposes for the repository, and without Pregate. Every CLI runs in an isolated machine under a temporary folder. Per session it records the engine's own hook decisions (event, tool, path, rule ids, denial message, evaluation time), classifies each denied file and rule as repaired, abandoned, worked-around or unknown, runs `pregate check --ratchet --base <pinned commit>` on the final tree of both arms, runs the task's `verify` command, and saves the final diff. A person labels the denials in [`session-trial-labels.json`](docs/benchmarks/session-trial-labels.json); the script never writes a label. `--plan` prints the sessions and their count and runs nothing, `--page` writes [the results page](docs/benchmarks/session-trial.md), and `--self-check` runs the whole pipeline with the real compiled engine, `pregate setup` and the registered hook commands against a scripted stand-in for the CLIs, which is what the tests run. Real sessions need `PREGATE_REAL=1` and spend model calls. The page says that no real session has been run, and self-check evidence is refused as published results.

## [0.0.7] - 2026-11-11

A small release. A project can carry its own reviewed launcher, which runs the engine its lock pins. Maintenance, a reproducible build and rollback are documented, and the upgrade and the rollback run as a test. The rest is how the project tests itself: CI takes about half the time, and hook latency is also read against the last release on the same runner. No rule and no contract format changed. See the [0.0.7 notes](docs/releases/0.0.7.md).

### Added

- **Maintenance, reproducible build and rollback are documented and tested.** [Maintenance, reproducible build and rollback](docs/guides/maintenance.md) says who releases Pregate, how to build a tag from a clean checkout, how a published archive is verified, and how a pinned project is upgraded and rolled back. An end-to-end test runs the upgrade and the rollback on every CI run with two real engines that differ only in version: the upgrade changes the pin and no rule, both engines deny the same edit for the same rule, and reverting the upgrade commit restores the first committed contract. The page states what a rebuild does not prove: two local builds were identical, and a local build of `v0.0.5` did not match the published archive.
- `pregate project launcher [--preview|--yes]` installs a reviewed launcher in the project at `.pregate/bin/pregate` (Windows: `pregate.cmd` and `project-launcher.ps1`). The launcher runs the engine that `.pregate/pregate.lock.json` pins from the user cache (`<DATA>/<version>/`) and never falls back to a launcher on PATH. Hook calls go through the engine's `--supervise` path. The command needs a valid engine pin and that engine in the cache (`pregate prepare`), and the files go through the same review and approval as a contract proposal. A hook call with a missing or empty cached engine denies (exit 2) and names the reason. On Windows the launcher calls PowerShell by its absolute path under `%SystemRoot%`. `pregate install` keeps this launcher; it removes only the launcher that 0.1.0 committed at the same path.
- **Hook latency is also read against the last release, on the same runner.** Over 60 CI runs the hosted macOS runner's own speed varied 3.4 times, and the regression gate compares with a fixed number under a 55% allowance: it failed twice on unchanged code, and on a fast runner a hook three times slower would have passed. `bun scripts/bench.ts --against <checkout>` builds the engine of another source checkout with the same toolchain, times both engines in turn on every sample, and reports the ratio per route. The `bench` and `latency` jobs run it against the last release tag as a step that cannot fail them. The existing gate is unchanged; a ratio becomes a gate only when its spread on hosted runners is known.

### Changed

- **Deadline tests bound the mechanism, not the machine.** Three tests proved a deadline with an upper bound on the whole command, engine start included: 3.5 s for a fitness verifier with a 500 ms deadline or an output budget, and 19 s for an issue transport with a 15 s deadline. On a memory-constrained Windows machine the engine start alone can exceed the margin. The bound is now on the life of the process the deadline ends, from its first line to the return of the command, and it is tighter (3 s, and 3 s past the 15 s deadline). Each such process also leaves a file only when it reaches its own exit, and the tests assert that the file is absent, which holds at any machine speed. No timeout was raised. Not validated on a low-memory Windows machine: none was available.
- **CI runs each suite once.** The Linux job ran the whole suite twice: `repo-hygiene.e2e` cloned the branch and ran every suite again inside the clone, 19 of the job's 39 minutes. The CI job is itself a fresh clone that installs and runs every suite, so the clone test now checks the tracked files, installs, type-checks and builds, and no longer repeats the suite. The Windows job ran `runtime`, `onboard`, `windows-powershell-script.e2e` and `windows-distribution.e2e` twice, and ran the latency bench that the `latency (windows-latest)` job already runs there. It now runs each suite once, in three parallel jobs with `bun test --shard`; the required check `windows` passes only when all three pass. No suite and no assertion was removed from a platform that had no other run of it.
- **The test suites start fewer and cheaper processes.** Per-test timings from CI showed that 3% of the tests used 83% of the Windows time, and that the cost was process starts, not the number of tests. Eight suites ran the engine from source for every call and now run the compiled engine. About 40 files compiled their own engine, 44 builds in one run; each now copies one build per flavour and test process. `dcouplr.test.ts` compiled the same lock 134 times and `prepare.e2e` packed the same archive four times; each does it once. No assertion changed.

- First-run instructions name one command, `pregate guide --preview`. ### Fixed
- A first layer map, or new layers added beside existing ones, no longer shows `WARNING: this may weaken protection` when the new globs share a path prefix with each other (for example `src/features/**/domain/**` and `src/features/**/application/**`). No file was in a layer before, so nothing can leave one. A new glob that can take a file from a layer that already had it still warns.
- One large generated or vendored file no longer stalls a check or an audit. Three questions with one answer per node were asked again for every candidate: the repair hint of each over-limit function or nested block walked the whole tree; `inside: { stopBy: end, has: … }` scanned the ancestor once per candidate; and a regex over a long enclosing node ran once per node inside it. Each is now answered once per node. On a 1.9 MB, 68,000-line JavaScript bundle, a check with 194 rules went from not finishing in two minutes to about 7 s on an M-series laptop, and the audit of the 13,499-file repository that contains it went from not finishing in ten minutes to 86 s. Findings are unchanged.
- **The shell guard no longer refuses `cd`, `bun test`, `pregate layers` or `pregate compile` in an enabled project.** The first friction measurement refused 32 of 101 routine commands; it now refuses 19. Three causes protected nothing. A shell builtin was looked up on `PATH`, and macOS ships `/usr/bin/cd`, `type`, `read`, `wait` and `umask` as scripts with a computed command name, so every `cd` was `shell-admin` there since 0.0.5. `bun test` was read as Bun running a script named `test` and refused when the project has a `test` directory. `pregate layers` and `pregate compile`, which only read or prepare a review, were not on the guard's list of commands an agent may run, although the skill tells the agent to run them. No form of those commands that applies a contract is allowed, and a script on `PATH`, a function named like a builtin, and `bun ./test` are still read. The remaining refusals (a read-only project script that imports a file-system module; a script whose text names a control command in prose) are listed on the measurement page for a maintainer decision.
- On Windows, a command that names a URL (`curl https://example.com/x`) no longer makes the pre hook fail. The guard checks each piece of a word as a path, the piece `//example.com/x` is a network path there, and its lookup failed with an error the engine did not expect. An unreachable network path is now treated as absent and judged where it is spelled.
- **`npm` and other installed tools that are scripts run in an enabled project.** Since 0.0.5 a command name found on `PATH` was read like a project script when the file was a script, so `npm install` and `npm test` were `shell-write`: the tool uses the file system. A native tool with the same behavior was never read. A script on `PATH` whose real file lies outside every enabled project is now read for control commands only. A script on `PATH` inside a project, such as `node_modules/.bin`, is still read whole. The trade is stated in [Guarantees and limits](docs/guarantees.md): a script planted in a `PATH` folder outside the project is no longer refused before it writes, and Stop, the pre-commit check and the CI ratchet judge the tree it leaves.
- **Antigravity 1.5.3 edits are gated again.** agy 1.5.3 renamed its edit tools to `write_file` and `edit_file`, with new argument names. The registered matcher named only the 1.2.14 tools, so no Pre hook ran and a forbidden edit was written; only Stop still blocked it. The matcher and the adapter cover both generations, the 1.5.3 payloads are recorded in `test/payloads/agy`, and four write tools the 1.5.3 binary names without a captured shape are refused inside a project instead of passing unread. The machine setup must run again to register the new matcher. Found by the real end-to-end run against the installed CLI.
- **A hung pinned engine no longer fails open for a project below the session's folder.** The launcher denied an engine failure only when the session's own folder had consent. With the session started in a parent folder and the edit in a nested enabled project, a pinned engine that hung let the write through. A redirect to a pinned engine now counts as evidence of a project, in the shell launcher and in the supervisor. Found by the real end-to-end run against Claude Code 2.1.322.

Sources: [Migrating to Cache Components](https://nextjs.org/docs/app/guides/migrating-to-cache-components) and the [route segment config](https://nextjs.org/docs/app/api-reference/file-conventions/route-segment-config).
- **`NEXT-CACHE-001` stays off under Cache Components.** The check does not run when `cacheComponents: true`, so a bare `fetch`, including one inside `use cache`, is not reported. In the previous model the default remains `auto no cache` and the rule stays off. Existing `fetch` `cache` and `next` options are not reported; the migration guide says they keep working.
- **`NEXT-REVAL-001` is now deny, and only when `cacheComponents: true`.** Without that flag, `export const revalidate = false` is the documented default and is not reported. With the flag, an exported `revalidate` on a page, layout, or route is denied, including `false`, `0`, and a positive number. Remove it and use `cacheLife` inside `use cache`, or leave the data uncached.
- **`NEXT-SERVER-EXPORT-001` newly denies server-file exports when Cache Components is on.** It still denies route segment exports from a `'use client'` page, layout, or route, and that list now includes `dynamicParams` and `fetchCache`. With `cacheComponents: true` it also denies server exports of `dynamic`, `dynamicParams`, `fetchCache`, and `runtime`, including `runtime = "nodejs"`. `preferredRegion`, `maxDuration`, `generateStaticParams`, `ensureStatic`, and `instant` are not flagged on the server.
- CI compiles the release engine once per run and the bench copies it (`scripts/compiled-engine.ts`, `PREGATE_COMPILED_ENGINE`). Lock-cache admission still verifies the full `compiledLockKey`. This is a CI and test speed change. It does not improve hook latency ([#42](https://github.com/pedroknigge/pregate/pull/42)).

### Fixed
- `pregate setup` no longer fails the whole install when one detected harness cannot be wired. Codex that does not confirm hook trust is a warning: `hooks.json` is left unchanged, and the message says to approve the PREGATE hooks in Codex with `/hooks`, then rerun `pregate setup`. Setup exits 0 when at least one harness was wired. It exits 1 when none were, or on a real error (a config it must not rewrite, a trust rollback that would drop someone else's hooks, an app-server that does not answer). `install.sh` and `install.ps1` both stop only on that non-zero exit. Output still names what was wired and what was not. `pregate guide` still applies a reviewed contract after a warning-only setup, and says agent-edit protection remains degraded. `pregate update` still switches the launcher and prepares project reviews in that case. Either command stops when setup prints an `ERROR:` line.
- Windows runs of the suite no longer require `sh` or `python3` on `PATH`, or a clone that already enabled long paths. The hook quote check runs Git for Windows `sh.exe` from `git --exec-path`, and skips only when that shell is not installed. Python inspection runs `py -3`, then `python`, then `python3`, and does not launch a WindowsApps alias. The fresh-clone check passes `-c core.longpaths=true`. The Git deadline check keeps a single `PATH` entry for its slow `git.exe`. A stock machine otherwise also keeps the system `Path`, runs the real Git, and returns before the deadline.
- The Windows verifier writes `report.json` when the run starts and again after each step. `finished` stays null until the end, so a killed run still leaves the steps that completed. A step that passes its time limit is recorded as timed out, and its process tree is killed (`taskkill /T /F /PID` on Windows, the process group on other systems). The run says to expect about an hour, warns when less than 2 GB of memory is free, and on Windows asks the system to stay awake until the verifier exits.
- `pregate demo` no longer exits when `stat` or `realpath` cannot read a PATH candidate. On Windows the Microsoft Store App Execution Alias for `python3` (`%LOCALAPPDATA%\Microsoft\WindowsApps\python3.exe`) is an `IO_REPARSE_TAG_APPEXECLINK` reparse point, and `stat` and `realpath` raise `EACCES`. That candidate is skipped and the next PATH entry is tried. When none resolves, that language's native checks are reported as not verified (`permission denied`), and the Python, Go, and Rust demos still run. The same failure emptied stdout for the demo test that surfaces a failing compiled engine, so the version error was reported as a JSON parse error.
- `JS-EVAL-001` flags indirect `eval`. A comma expression that yields `eval` was missed, including `(0, eval)(code)`, `(1, eval)(code)`, and `(void 0, eval)(code)`. `globalThis.eval(code)` and `window.eval(code)` stay flagged. A name that only contains those letters, such as `evaluate(code)` or `item.evaluate(code)`, is not. The javascript pack is 1.2.1 and `javascript/safety/no-eval-call` is 1.0.1.
- `pregate scan` recommends the Svelte pack (`svelte/runes` and `svelte/stores`, catalog `svelte@1.2.0`) when a project is Svelte. Exact `svelte` dependencies and peer dependencies are confined to the package that declares them, the same way Vue declarations are. `@sveltejs/*` dependencies and peer dependencies count too. The Svelte repository is the package named `svelte` and does not depend on `svelte`, so that package name counts. A `.svelte` source file or a `svelte.config.*` file counts as well; those files do not add a package owner. A devDependency and a similarly named package, such as `eslint-plugin-svelte`, do not.
- Scan and guide no longer recommend a pack from evidence that lives only in a docs site, examples tree, or website folder. Folder names `doc`, `docs`, `documentation`, `website`, `example`, `examples`, `sample`, `samples`, `demo`, `demos`, and `playground` are ignored at any depth, including `packages/docs`. Evidence only under `.github/`, or only in a `scripts/` directory of at most three inventoried files, is ignored the same way. A `.svelte` file, `svelte.config.*`, or Svelte dependency that appears only in those folders does not select the Svelte pack. A Next.js or React dependency in the root `package.json` or in a primary app package such as `apps/web`, a primary Svelte app, and Python source or project metadata outside those folders, still recommends that pack.

## [0.0.3] - 2026-11-03

What changed for people installing or gating a repository. **Windows users of 0.0.2 should upgrade.** Two bugs on that release could let an edit through on Windows without a finding. Notes: [0.0.3](docs/releases/0.0.3.md). The previous public tag is [v0.0.2](https://github.com/pedroknigge/pregate/releases/tag/v0.0.2).

### Added
- Pack precision on a pinned set of public repositories, one or more for each parsed language. `scripts/bench-audit-repos.ts --precision` counts findings per pack. Sample precision is published only for the maintainer-labeled packs in `bench/labels/`. Packs with no labels stay unmeasured. The method and the limits are in `docs/guides/rule-precision.md`.
- CI measures the compiled Pre hook on 200-line and 2,000-line files on Linux, macOS, and Windows. The required check stays `bench` on `ubuntu-latest`; macOS and Windows run the same gate. Each route's baseline is the median of eight hosted median p95s. The gate fails when a new median is more than 55% above that. The widest run in that sample was 44.7% above its median, and the extra 10 points keep a repeat of that slow run inside the limit.
- When Git cannot be used, Pregate still denies the edit and names the failure. `git-missing` means `git` is not on PATH (install Git). `git-not-repository` means this directory is not a Git repository, or its `.git` was removed (`git init`, or restore `.git`; a scratch directory can be left with `pregate disable`). `git-error` means Git ran and returned some other error (`git status`, or `pregate disable` for a scratch directory).

### Changed
- Codex 0.166.0 is the verified CLI. For Bash, `PreToolUse` `cwd` is the command's resolved working directory ([openai/codex#57198](https://github.com/openai/codex/pull/57198); permission and post-tool hooks do the same in [#57203](https://github.com/openai/codex/pull/57203)). Relative shell paths resolve against that directory. A working directory in a subfolder still uses the same project root. A working directory outside the repository does not drop that project's gate, and a write that lands in the session project is still judged by that project's contract rather than by another project's. `apply_patch`, `SessionStart`, and `Stop` still carry the session directory. The payload has no version field and the same shape as 0.159.2, so 0.166.0 is the minimum supported Codex release.
- The README states the platforms this release actually supports: macOS ARM64 is stable, and Linux and Windows are experimental. It summarizes what a global setup writes, how `disable` and `uninstall` remove it, and that advisor mode or the GitHub Action is the way to start. The install guide remains the place for checksums, signatures, and updates.
- Each release archive carries the GNU Library General Public License, version 2, for the JavaScriptCore that the Bun 1.4.4 runtime links statically, and the full GNU Lesser General Public License, version 2.1, for tinycc. The notice gives permanent links to the Bun tag `bun-v1.4.4`, WebKit commit `d6375c72affe0f70222cdcb45012b10f0bf3a9d5`, and tinycc commit `05f0fafaa3be31e31d7b4b5c17dc60f62c991171`, plus the steps to rebuild. Setup copies that notice next to the installed engine.

### Fixed
- **Windows: an unaccepted preset made the hook skip the edit.** On Windows, `git add` rewrites the preset's timestamp, and the file clock can sit ahead of the hook. Pregate then treated the project as if it had no contract. The pre-edit hook exited successfully and recorded nothing, so the edit was allowed. 0.0.3 denies that call (`lock-stale`) and says to commit the preset and open a new session. The edit does not land silently.
- **Windows: an 8.3 short path and its long path looked like different projects.** Windows sometimes reports a short name such as `C:\Users\ME~1\...` and sometimes the long name. Consent stored under one spelling did not match the other, so a project you had agreed to protect looked unconsented and the hook exited without a finding. 0.0.3 treats those spellings as the same directory, by the file's identity rather than the letters in the path.
- Inside an enabled root, a shell, interpreter, or `make` command whose script is not a literal path is denied (`bash "$SCRIPT"`, `sh "$X"`, `bash < "$S"`, `python3 "$P"`, `node "$P"`, `make -f "$F"`, `powershell -File $P`). A bare command name is resolved on `PATH` and scanned when that file is a script. The denial says why and how to name the script literally. Concatenation and encodings the decoder does not recognize stay residual limits.
- Catches on the trust path no longer hide an unexpected error. A read or parse failure that is not the expected kind propagates, so the hook denies it. A catch that still handles every error says why that fallback is fail-closed, and CI rejects a new unannotated catch-all in `src/`.
- Living docs, the skill, and installer messages name 0.0.3. They do not send readers to pre-rename versions, private-repository downloads, or release files this repository does not publish.

## [0.0.2] - 2026-11-02

What changed for people installing or gating a repository. The first public tag remains [0.0.1](docs/releases/0.0.1.md).

### Added
- Pre hooks reuse a compiled lock when the contract and this build are unchanged. Admission still compares that compiler output with the lock bytes, and a corrupt cache is recompiled.
- Release archives and `SHA256SUMS` are signed with keyless cosign (GitHub OIDC). Each signed file is published as a `.bundle`, and the workflow also attests build provenance. Installers and the GitHub Action refuse a checksum or signature that does not match. Set `require-signature: false` only for a release that was cut before signing.
- The no-new ratchet keeps debt that moved with an unchanged function body, and still treats a copy sitting next to the original as new debt. A symlink is judged by the path you spelled: a target in another enabled root is that root's problem, and a target in no enabled root is denied.
- `docs/guarantees.md` records, from an adversarial end-to-end run, where each ratchet and trust-boundary case is sound, best-effort, or still a gap.
- A findings count for each bundled pack against pinned repositories. Unlabeled findings stay unlabeled. The report does not turn them into a false-positive rate.
- The GitHub Action has a default for each mode. `check` scans the whole tree. `audit` no longer receives `--all` (that flag is a usage error). `ratchet` requires `base` and stops before it can fall through to a full check. A SARIF path follows the same rules.
- CI, release, native-release, the bootstrap jobs, `action.yml`, and the generated consumer workflow pin every GitHub action to a full commit SHA with a `# vX` comment. A lint fails if one is unpinned.
- The generated CI workflow reads the engine version from the base branch lock and verifies the cosign bundles before it unpacks the binary.

### Changed
- The default TypeScript contract was recalibrated against mature repositories. Some findings that used to deny are now warnings. A project that needs the old hard stop opts that rule into deny.
- Hook pre denies more ways around control commands: inline interpreters, scripts fed on stdin, scripts with no suffix, Makefiles, and edits of user-level harness settings. `pregate approve` applies only after a person confirms it on a terminal.
- There is still no npm package. Install from the GitHub release. The README and install guide say so.
- The Action's default version is 0.0.2, the release this tree publishes. `scripts/build.ts` refuses to pack installers or an Action whose version disagrees with `package.json`. The previous default asked for v0.0.1 signature bundles that were not published.
- Signing tests stay offline unless `PREGATE_E2E_SIGSTORE=1`. CI sets that and uses real cosign. A local `bun test` does not download cosign or contact Sigstore.
- Docs generation sorts the same way on every machine. Bench and smoke approve `enable` at a terminal, so they do not skip the human gate. Stdout and stderr finish writing when the pipe is non-blocking, which matters for hook decisions on Windows and in CI.
- On Windows, setup waits for an on-access scanner to release a new `pregate.exe` before renaming it into place. Ordinary atomic writes use that same retry. A lock that outlasts the wait still fails.
- `node_modules` is not tracked.
- **Action needed for unattended jobs:** `CI` in the environment no longer approves anything. Tools and agent sessions set `CI` too, so it was never a safe signal that nobody was at the keyboard. A job that really runs without a person (for example, one that calls `pregate enable --yes` or `uninstall --yes`) now sets `PREGATE_UNATTENDED_APPROVAL=1` itself. The shell guard denies an agent command that sets it.
- Development, CI, and release jobs install Bun 1.4.4 from `.bun-version`. Bun 1.4.2 can segfault while leaving `bun test --isolate` after the tests have passed ([oven-sh/bun#43056](https://github.com/oven-sh/bun/issues/43056)); that crash is fixed in 1.4.3 and later. The Windows suite is the job that runs with `--isolate`. GitHub Actions stay pinned to a full commit SHA.

### Fixed
- A compiled-lock cache write no longer drops every error in an empty `catch`. A filesystem failure leaves the cache unwritten and admission stands, so the next hook recompiles. Any other error propagates.
- Terminal approval reads `/dev/tty` directly. Bun 1.4.4 pauses stdin when a readline stream on that device is destroyed, so the next question never saw what was typed.
- Looking up the project that started a hook no longer drops every error in an empty `catch`. A path with no existing ancestor is still not a project. A symlink loop or any other error propagates.
- The two known symlink gaps stay skipped, and they are not a passing attack. They use `test.skipIf` until `PREGATE_RUN_KNOWN_GAPS` is set, so `check --all` no longer sees an unconditional `test.skip`.

Thank you to the pre-release reviewers who found these trust-boundary holes. Each one now has an end-to-end test that runs the compiled binary.
- **Loosening the contract needs a person.** Before this fix, a short script could switch rules to `advisor` and run `pregate preset compile`, and every check accepted the result. Now:
  - `check --ratchet` compares the base lock with the head lock and fails on any loosening. It prints a digest for that exact change. A maintainer accepts it by putting the digest in the repository variable `PREGATE_ACCEPT_CONTRACT`, which a pull request cannot edit. The Action has a matching `accept-contract` input. Protect `.pregate/` and `.github/workflows/` with CODEOWNERS so a pull request cannot rewrite the check either.
  - Stop and the pre-commit hook block a looser lock unless this machine recorded a person approving that exact lock. These local records help, but the same user can forge them. CI is the boundary.
  - `preset compile` asks a person before it writes a looser lock.
  - Scripts that run `preset compile`/`apply`, `init` or `promote` without `--preview`, `feedback apply`, `storage apply` or `issue submit` count as control commands, like `approve` and `disable` already did.
- **Removing consent is no longer silent.** If consent for a project is disabled or deleted mid-session, Stop warns and names the project, and `pregate status` warns for a day. This works on Linux, macOS and Windows, even when every consent record is gone.
- **Git history commands are writes.** `reset --hard`, `checkout <commit>`, `switch --detach`, `stash`, `clean -f`, `cherry-pick`, `revert`, `read-tree` and `checkout-index` are judged by the files Git says they would change. They are denied when they would change `.pregate/`.
- **Agents cannot approve through a native permission prompt.** Every harness denies an approval command the agent issues and tells the person what to type: `! pregate approve <code>` in Claude Code, Codex, Grok and agy, or a separate terminal in Cursor.
- **The control-command scan is harder to dodge.** It joins lines split with `\`, a backtick or `^`, reads the whole script instead of stopping at 1 MiB (anything over 64 MiB is refused), and decodes UTF-16 and UTF-32 scripts such as Windows PowerShell files. Inline Python, Node, Bun, Deno, Perl, Ruby and PHP code is judged by the write calls it makes, not by whether an argument looks like a file name.
- `docs/guarantees.md` and `SECURITY.md` now say exactly which of these protections are enforced in CI, which are best-effort on a local machine, and which detect tampering rather than prevent it.
